# دعوت و لغو دسترسی دستیاران — طرح پیاده‌سازی

این مرحله یک مسیر سروری اولیه برای دعوت دستیار با ایمیل و لغو دسترسی اضافه می‌کند؛ به رابط نمایشی متصل نیست و تا آماده‌شدن پیکربندی/آزمون‌ها نباید برای حساب واقعی استفاده شود.

## فایل‌ها
- `supabase/functions/admin-staff-access/index.ts`: تنها endpoint برای `invite` و `revoke`.
- `supabase/migrations/20261016200000_admin_staff_audit_log.sql`: جدول ثبت رویدادهای دعوت/لغو دسترسی.

## کنترل‌های امنیتی
- هر درخواست باید Bearer token معتبر داشته باشد و سرور با `auth.getUser(token)` آن را اعتبارسنجی کند.
- فقط کاربری که `public.is_primary_admin()` برای او `true` برمی‌گرداند اجازه اجرا دارد؛ نقش متنی `admin` به‌تنهایی کافی نیست.
- کلید service role فقط در Secrets سمت Supabase Edge Function می‌ماند و هرگز به مرورگر نمی‌رود.
- فهرست مجوزها در سمت سرور allowlist شده است؛ عنوان و ایمیل اعتبارسنجی می‌شوند.
- دستیار نقش `admin` نمی‌گیرد؛ دسترسی او فقط از رکورد `admin_staff_permissions` می‌آید.
- لغو دسترسی ابتدا `is_active=false` می‌کند تا `has_admin_permission` فوراً دسترسی داده‌ای را رد کند، سپس تلاش می‌کند ورود Auth را مسدود کند.
- رویدادهای دعوت موفق/ناموفق و لغو دسترسی ثبت می‌شوند. گزارش‌ها نباید شامل توکن، رمز یا لینک دعوت باشند.

## پیش‌نیازهای اجباری پیش از استفاده
1. بررسی کامل زنجیره migrationهای امنیتی و اجرای آن‌ها در پروژه Supabase آزمایشی، نه production.
2. تنظیم `primary_admin_id` فقط از مسیر مورد اعتماد و تأیید هویت مدیر اصلی.
3. تنظیم Secrets تابع: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `STAFF_INVITE_REDIRECT_URL` و در صورت نیاز `STAFF_ADMIN_ALLOWED_ORIGIN`.
4. تنظیم URL مقصد دعوت در allow-list مربوط به Auth؛ مسیر پذیرش دعوت/تنظیم رمز باید واقعاً در برنامه پیاده‌سازی و آزمایش شود.
5. اتصال صفحه مدیریت دستیارها به endpoint فقط پس از جایگزینی ورود نمایشی با Supabase Auth واقعی و MFA مدیر اصلی.

## آزمون‌های لازم در محیط آزمایشی
- بدون توکن، توکن منقضی، و حساب عادی: رد با 401/403.
- مدیر اصلی با نشست AAL1: رد با 403 و \`mfa_required\`; مدیر اصلی با نشست AAL2: ادامهٔ بررسی مجوز.
- ایمیل نامعتبر، مجوز ناشناخته/تکراری، عنوان کوتاه/بلند: رد درخواست.
- دعوت موفق: یک حساب غیر-admin، رکورد permission و audit log ایجاد شود و ایمیل یک‌بار برای همان حساب ارسال شود.
- ایمیل تکراری یا خطای ارسال: دسترسی اضافی ایجاد نشود.
- لغو دسترسی: `is_active=false` و رد فوری `has_admin_permission`; سپس بررسی مسدودشدن ورود.
- خطای نوشتن permission/audit: هیچ دعوت نیمه‌کاره قابل استفاده باقی نماند.
- آزمون RLS برای همه جدول‌های حساس و بررسی این نکته که مجوزهای write هنوز پیاده‌سازی نشده‌اند.

## محدودیت شناخته‌شده
کد فعلی پروژه در `src/contexts/AuthContext.tsx` نشست محلی نمایشی می‌سازد و `src/main.tsx` پنل admin را با query/path نمایش می‌دهد؛ بنابراین رابط فعلی احراز هویت مدیر نیست. این endpoint به همین دلیل هنوز از رابط کاربری فراخوانی نمی‌شود. همچنین باید سازگاری trigger ساخت پروفایل و نوع حساب‌های invite شده در پروژه آزمایشی بررسی شود. هیچ migration یا function در Supabase اجرا/منتشر نشده است.

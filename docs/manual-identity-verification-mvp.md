# معماری احراز هویت دستی براه (MVP)

## هدف نسخه فعلی

- ابتدا استقبال از براه سنجیده شود و تا قبل از اثبات نیاز، هزینه سرویس احراز هویت خودکار پرداخت نشود.
- یک جریان مشترک برای راننده و صاحب بار طراحی شود: راهنمای احراز هویت، مدرک شناسایی، عکس سلفی و وضعیت قابل پیگیری.
- تماس با صاحب بار فقط پس از وضعیت تأییدشده مجاز باشد.
- منطق وضعیت به سرویس ارائه‌دهنده گره نخورد تا اتصال به یک سرویس خودکار در آینده بدون بازنویسی UI ممکن بماند.

## وضعیت این پیاده‌سازی

این مخزن در حال حاضر از ورود آزمایشی/localStorage استفاده می‌کند و احراز هویت Supabase در مسیر ورود فعال نیست. بنابراین UI و وضعیت «در انتظار بررسی» در این شاخه فقط نمایشی‌اند؛ تصویر مدرک و سلفی به سرور ارسال یا برای مدیر قابل مشاهده نمی‌شوند. تا زمانی که ورود واقعی، upload امن و API سمت سرور متصل نشده، این نسخه برای تأیید هویت واقعی یا عرضه عمومیِ محافظت‌شده آماده نیست.

وضعیت آزمایشی با کلید جداگانه برای هر کاربر در مرورگر ذخیره می‌شود. نه کد ملی، نه تصویر مدرک، نه سلفی و نه توکن دسترسی در localStorage ذخیره نمی‌شوند. وضعیت مرورگر مرز امنیتی نیست و هرگز نباید به‌تنهایی برای اعطای دسترسی در تولید استفاده شود.

## مسیر تجربه کاربر

1. کاربر وارد می‌شود و بدون احراز هویت می‌تواند بارها را جست‌وجو کند.
2. اولین تلاش برای تماس با صاحب بار، پنجره «ابتدا احراز هویت کنید» را نمایش می‌دهد.
3. دکمه «متوجه شدم» صفحه توضیح چرایی احراز هویت را باز می‌کند.
4. دکمه «ادامه» فرم مدرک شناسایی و سلفی را باز می‌کند.
5. تا زمان تأیید واقعی سمت سرور، تماس باز نمی‌شود. مسیرهای تماس در رابط فعلی نیز همین قاعده را اعمال می‌کنند.

## قرارداد داده پیشنهادی

وضعیت‌ها: unverified، pending، needs_correction، verified و rejected.

جدول identity_verification_submissions برای هر ارسال یک رکورد تاریخچه نگه می‌دارد. فایل‌ها باید فقط در bucket خصوصی identity-documents ذخیره شوند؛ جدول تنها مسیر فایل‌ها، چهار رقم پایانی شناسه ملی، اثرانگشت کلیددار، وضعیت و متادیتای بررسی را نگه می‌دارد. مقدار خام کد ملی یا تصویر نباید در جدول، گزارش‌ها یا پیام خطا ذخیره شود.

اثر انگشت شناسه ملی باید در Edge Function با HMAC و راز سمت سرور تولید شود؛ هش ساده شناسه ملی ۱۰ رقمی در برابر حدس‌زدن آفلاین کافی نیست. درج درخواست باید از مسیر سمت سرور با اعتبارسنجی کاربر، نقش و مسیر فایل انجام شود. سیاست RLS عمداً درج یا تغییر وضعیت توسط کاربر عادی را مجاز نمی‌کند. تنها مدیر مجاز می‌تواند نتیجه بررسی را تغییر دهد و تغییر وضعیت در identity_verification_events ثبت می‌شود.

## معماری قابل تعویض در آینده

فایل src/features/verification/verificationStatus.ts نوع وضعیت و مرز repository را تعریف می‌کند. adapter آزمایشی فقط وضعیت را در مرورگر نگه می‌دارد. adapter تولید باید از API سمت سرور برای این عملیات استفاده کند:

- getStatus(userId) — دریافت وضعیت معتبر از سرور.
- submitManualReview(...) — آپلود در Storage خصوصی و ثبت درخواست از طریق Edge Function.
- review(submissionId, decision, note) — فقط از مسیر مدیر مجاز؛ ثبت تصمیم، زمان و شناسه مدیر.
- providerهای خودکار در آینده باید همین قرارداد را اجرا کنند و خروجی‌شان مستقیم و بدون بررسی سیاست‌های براه وضعیت verified نشود.

## گام‌های لازم پیش از تولید

1. اجرای migration جدید در محیط Supabase آزمایشی و بازبینی RLS و Storage policies.
2. فعال‌کردن احراز هویت واقعی Supabase و حذف ورود آزمایشی hard-coded از مسیر تولید.
3. ساخت Edge Functionهای submit/review؛ اعتبارسنجی نوع و اندازه فایل، مسیرهای storage، HMAC شناسه ملی، جلوگیری از درخواست تکراری و محدودیت نرخ.
4. اتصال فرم به upload خصوصی و API، و ایجاد صف مدیر برای مشاهده فایل‌ها و ثبت نتیجه.
5. کنترل تماس و عملیات حساس در سمت سرور/API؛ کنترل UI به‌تنهایی قابل دور زدن است.
6. تعیین سیاست نگهداری و حذف مدارک، سطح دسترسی مدیران، ثبت رویدادهای دسترسی و متن رضایت کاربر.
7. آزمون نقش‌های راننده/صاحب بار، حساب‌های تکراری، مدارک نامعتبر و خطاهای سرویس، سپس اتصال سرویس خودکار فقط در صورت نیاز.

## نکته عملیاتی

Migration آماده‌سازی ساختار داده و محدودیت دسترسی است و به‌تنهایی فرم را به Supabase متصل نمی‌کند. این PR سرویس خودکار نمی‌خرد و به هیچ ارائه‌دهنده احراز هویت وابسته نیست.

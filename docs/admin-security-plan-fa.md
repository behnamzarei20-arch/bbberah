# طرح امن‌سازی پنل مدیریت براه

وضعیت: طرح اولیه؛ هنوز هیچ تغییر امنیتی اجرایی یا انتشار عمومی انجام نشده است.

## هدف‌ها و انتخاب‌های تأییدشده
- ورود مدیر با رمز عبور و تأیید دومرحله‌ای اجباری.
- اجازه ورود از چند دستگاه، با مشاهده و لغو نشست‌ها.
- بازیابی امن حساب مدیر.
- فقط یک حساب مدیرِ صریحاً مجاز؛ ثبت‌نام عمومی نباید بتواند نقش مدیر بگیرد.
- رابط کاربری فارسی و سازگار با موبایل.

## وضعیت فعلی که باید اصلاح شود
- `src/main.tsx` مسیرهایی مانند `/admin` و پارامتر `?admin` را پیش از بررسی نشست/نقش نمایش می‌دهد.
- `src/contexts/AuthContext.tsx` از حساب‌ها و نشست‌های نمایشی در `localStorage` استفاده می‌کند و ورود آزمایشی می‌سازد.
- `src/pages/auth/AuthPage.tsx` از کد ثابت نمایشی `12345` استفاده می‌کند؛ این کد احراز هویت واقعی نیست.
- `src/lib/supabase.ts` در نبود تنظیمات محیطی به سرویس جایگزین نمایشی می‌رود.
- `src/pages/admin/AdminPanel.tsx` داده‌های نمونه نشان می‌دهد و هنوز به سامانه واقعیِ مجوزدار متصل نیست.

## معماری پیشنهادی
1. **رابط کاربری استاتیک:** می‌تواند فعلاً روی GitHub Pages بماند؛ هیچ داده محرمانه یا مجوزی نباید فقط به کنترل‌های مرورگر متکی باشد.
2. **سرویس هویت:** Supabase Auth یا سرویس مشابه، با رمز عبور و MFA اجباری برای مدیر. پیش از انتخاب نهایی باید تنظیمات و دسترسی واقعی پروژه بررسی شود.
3. **مجوز مدیر:** allowlist/شناسه حساب مدیر در منبع مورد اعتماد سمت سرور؛ هر درخواست حساس باید مجوز را سمت سرور بررسی کند. اطلاعات نقش در metadata قابل ویرایش کاربر برای اعطای دسترسی کافی نیست.
4. **پایگاه داده:** سیاست‌های دسترسی حداقلی و پیش‌فرضِ منع دسترسی؛ دسترسی هر جدول و عملیات مدیریتی جداگانه بررسی شود. هیچ کلید service-role یا راز سرور در bundle مرورگر یا مخزن عمومی قرار نگیرد.
5. **نشست‌ها و دستگاه‌ها:** نشست‌های قابل مشاهده، ابطال نشست منفرد/همه نشست‌ها، خروج هنگام تغییر حساس و زمان انقضای مناسب. چنددستگاهی بودن به معنی اعتماد خودکار به هر دستگاه نیست.
6. **بازیابی:** ایمیل بازیابیِ تأییدشده یا روش امن پشتیبانی‌شده، توکن‌های یک‌بارمصرف و منقضی‌شونده، اطلاع‌رسانی تغییرات و امکان لغو نشست‌ها. کدهای بازیابی باید خارج از همین حساب و امن نگهداری شوند.
7. **ثبت امنیتی:** ثبت سمت سرور برای ورود موفق/ناموفق، تغییر MFA/رمز، بازیابی، لغو نشست و عملیات مدیر؛ هرگز رمز، کد MFA یا توکن را ثبت نکنیم.
8. **محافظت تکمیلی:** محدودسازی تلاش ورود، خطاهای عمومی برای جلوگیری از افشای وجود حساب، HTTPS، سیاست‌های امن نشست، مدیریت وابستگی‌ها و بازبینی تنظیمات استقرار.

## مراحل اجرایی پیشنهادی
### مرحله A — بررسی و آماده‌سازی (کم‌ریسک)
- بررسی وجود پروژه Supabase واقعی، تنظیمات محیطی GitHub Actions، طرح پایگاه داده، سیاست‌های RLS و روش امن تنظیم رازها.
- نگه داشتن این طرح در شاخه جدا؛ بدون تغییر `main` و بدون انتشار.
- تهیه فهرست دقیق فایل‌ها و مهاجرت‌های مورد نیاز بر اساس تنظیمات واقعی.

### مرحله B — بستن دسترسی نمایشی
- حذف bypass مربوط به `?admin=1` و جلوگیری از render شدن AdminPanel بدون نشست معتبر و مجوز مدیر.
- حذف مسیر ورود نمایشی و کد ثابت OTP از جریان ورود واقعی.
- تا زمان تکمیل اتصال سمت سرور، نمایش پیام «پنل مدیریت هنوز پیکربندی نشده» به‌جای نمایش پنل به‌عنوان محیط واقعی.

### مرحله C — هویت و مجوز سمت سرور
- اتصال ورود رمز عبور و اجبار MFA برای مدیر.
- تعریف دقیق حساب مدیر مجاز و رد سایر حساب‌ها.
- تنظیم RLS و کنترل مجوز برای هر عملیات حساس؛ کلیدهای محرمانه فقط در محیط سمت سرور.

### مرحله D — بازیابی و نشست‌ها
- پیاده‌سازی بازیابی امن، فهرست نشست‌ها، لغو نشست‌ها و رویدادهای حساب.

### مرحله E — آزمون و بازبینی
- ورود ناشناس و مسیر مستقیم admin باید رد شود.
- کاربر عادی نباید صفحه یا داده/عملیات مدیریتی را ببیند یا اجرا کند.
- مدیر بدون MFA نباید دسترسی مدیریتی بگیرد.
- تست بازیابی، انقضای نشست، لغو نشست، محدودسازی تلاش‌ها و سیاست‌های RLS.
- build/typecheck و بررسی دستی قبل از پیشنهاد ادغام.

## نقاط نیازمند تأیید صریح
- افزودن/تغییر فایل‌های اجرایی و مهاجرت پایگاه داده.
- تغییر تنظیمات Supabase، DNS یا رازهای GitHub Actions.
- حذف یا تغییر هر داده موجود.
- ادغام به `main` و هر انتشار عمومی.

هیچ رمز، کلید API محرمانه یا کد بازیابی را در چت یا فایل‌های مخزن عمومی قرار ندهید.
